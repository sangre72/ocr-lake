## 1. 업무 의도

### 1-1. 왜 오인식 대처가 필요한가

OCR은 절대 100% 정확하지 않다. 오늘 리서치(`docs/research/ocr-technology-trends.md`)에서도 정확도·비용·
속도가 트레이드오프 관계임을 확인했고, ocr-lake가 현재 채택한 Tesseract(가벼움·저비용 우선)는 특히
다음 상황에서 오인식이 잦다:

- 숫자·기호 혼동(`0`↔`O`, `1`↔`l`↔`I`, `5`↔`S`)
- 흐릿하거나 기울어진 촬영 이미지
- 표·다단 레이아웃에서 컬럼 순서가 뒤섞임
- 한글 음절 조합 오인식(`docs/research/ocr-technology-trends.md` §3 한글 특화 이슈 참고)

**문제**: 틀린 텍스트가 검수 없이 그대로 `ocr_records.extracted_text`에 저장되고, 이후 §14-1 AI 구조화
파싱(MLX)의 입력으로도 그대로 흘러 들어간다. 원본이 틀리면 구조화 결과(금액·날짜 등)도 함께 틀리고,
그 오류가 다운스트림 업무 처리·검색까지 전파된다.

### 1-2. 누가 무슨 판단을 하는가

| 역할 | 판단 내용 |
|---|---|
| **업로더 본인**(텔레그램 사용자 또는 웹 업로드자) | "방금 처리된 결과가 맞는지" 1차 확인. 본인이 원본 이미지 맥락을 가장 잘 안다. |
| **검수자**(향후 다중 사용자 확장 시) | 웹 이력 목록에서 과거 레코드를 사후 검토·수정(이번 스코프는 업로더 본인 셀프 수정까지만 — 별도 검수자 역할·권한 분리는 로드맵 §5 참고). |

이번 설계는 **1차로 업로더 본인의 셀프 수정**에 집중한다. 다중 사용자 권한 분리(예: ADMIN이 타인 기록을
수정)는 이 프로젝트가 아직 단일 사용자 로컬 도구 단계(`TELEGRAM_ALLOWED_CHAT_IDS` 기반 허용목록만 존재,
역할 체계 없음)라 스코프 밖이다.

### 1-3. 성공 기준

1. 사용자가 OCR 결과를 보고 "틀렸다"고 판단할 근거(신뢰도 표시 등)를 화면/메시지에서 확인할 수 있다.
2. 틀린 부분을 원본 이미지를 보면서 직접 고칠 수 있다(원본과 텍스트를 나란히 대조).
3. 수정 후 저장하면, **원본 OCR 결과와 수정본이 둘 다 남는다**(원본을 덮어쓰지 않음 — 감사 추적·재학습
   데이터로 활용 가능성 보존).
4. 수정 이력(언제 수정됐는지)이 API 응답에 노출되어, 이후 이 레코드를 다시 보는 사람이 "이건 사람이
   검수한 결과"임을 알 수 있다.

## 2. 오인식 발견 방법 — 설계안 비교

3가지 후보를 검토했다. **전부 한 번에 구현하지 않고 우선순위를 매긴다**(과설계 방지).

### (a) confidence 기반 자동 플래그

- **방법**: `core/classify/engine.py`의 `_text_signal()`이 이미 Tesseract `image_to_data`에서 단어별
  confidence를 뽑고 있다. 이 계산 로직을 **재사용**해 개별 단어의 confidence를 함께 반환하도록 확장하면,
  낮은 confidence 단어를 화면에서 하이라이트(예: 노란 배경)할 수 있다.
- **장점**: 재사용 가능한 기존 로직이 있어 구현 비용이 낮다(신규 알고리즘 불요). 사람이 "어디부터 볼지"
  우선순위를 자동으로 좁혀준다.
- **단점**: confidence가 높아도 실제로 틀릴 수 있고(예: 문맥상 말이 안 되는 단어인데 개별 문자는 또렷),
  confidence가 낮아도 맞을 수 있다(단순 잡음). 100% 신뢰 지표는 아니다.

### (b) 유저 능동 신고

- **방법**: 웹/텔레그램 결과 화면에 "이 결과 틀렸어요" 버튼 → 클릭 시 수정 모드 진입.
- **장점**: 구현이 가장 단순하다(버튼 1개 + 상태 전환). 사람의 판단을 100% 신뢰하므로 오탐/미탐 이슈가 없다.
- **단점**: 능동적으로 신고하지 않으면 틀린 결과가 계속 방치된다(발견 자체를 사람에게 전적으로 의존).

### (c) 구조화 정합성 휴리스틱

- **방법**: §14-1 MLX 구조화 단계에서 원본 텍스트와 구조화 결과(예: `total` 필드)의 타입·형식이 안 맞으면
  (금액 필드에 문자가 섞임 등) 경고 플래그를 붙인다.
- **장점**: 구조화까지 실행한 경우 추가 신호를 얻을 수 있다.
- **단점**: 구조화를 거치지 않은 레코드(아직 온디맨드라 구조화 안 한 경우가 많음, `docs/tech-spec.md` §9
  참고)에는 적용이 안 된다. 구조화 자체도 아직 로컬 LLM 초기 구현이라 안정성이 검증 중이라, 이 신호에
  의존도를 높이면 이중으로 불확실성이 쌓인다.

### 제안: 1차로 **(b) 유저 능동 신고 + 수정 UI**를 채택, (a)는 그 위에 보조 신호로 얹는다

**근거**:
1. (b)는 구현 비용이 가장 낮고, 사람의 최종 판단을 그대로 신뢰하므로 즉시 실용적 가치를 낸다.
2. (a)는 (b)의 UI(텍스트 수정 화면)가 이미 있어야 "하이라이트해서 보여줄 곳"이 생긴다 — 즉 (a)는 (b) 위에
   자연스럽게 얹히는 **점진적 개선**이다. (b) 먼저 만들고 (a)는 후속으로 붙이면 재작업이 없다.
3. (c)는 구조화 기능 자체가 아직 온디맨드·초기 단계라 이 설계보다 후순위가 맞다.

**우선순위**: (b) 수정 UI(1차) → (a) confidence 하이라이트(2차, (b) 화면에 추가) → (c) 구조화 정합성
경고(3차, §14-1 구조화가 더 안정화된 뒤).

## 3. 휴먼 인터페이스 설계

### 3-1. 웹: RecordDetail 화면 확장

현재 `web/frontend/components/RecordDetail.tsx`(실측: `<pre>`로 `extractedText`를 읽기 전용 표시)에
다음을 추가한다.

```
┌─────────────────────────────────────────────┐
│ [문서로 인식]  2026-08-22 12:00               │
├───────────────────┬───────────────────────────┤
│                   │  추출된 텍스트              │
│  원본 이미지        │  ┌─────────────────────┐  │
│  (imagePath 참조)  │  │ (편집 가능한 textarea) │  │
│                   │  └─────────────────────┘  │
│                   │  [저장] [원본 OCR 결과 보기] │
└───────────────────┴───────────────────────────┘
```

- **원본 대조 검수 뷰**: 이미지와 텍스트를 좌우(또는 375px 모바일에서는 상하)로 나란히 배치.
  `imagePath`(이미 `ocr_records`에 저장돼 있음, `docs/tech-spec.md` §7 참고)를 `<img>`로 렌더링.
- **편집 가능한 필드**: 기본은 읽기 전용 `<pre>` 대신 `<textarea>`(또는 편집 모드 토글 버튼으로 전환).
  저장 시 `PATCH /api/records/{id}` 같은 신규 엔드포인트(§4에서 스키마 제안)로 `corrected_text` 갱신.
- **"원본 OCR 결과 보기"**: 수정 후에도 최초 OCR 원문을 접어서(collapsible) 대조 가능하게 남겨둔다.
- **접근성**(accessibility-guideline.md 웹 파트 적용):
  - `<textarea>`에 `<label>` 연결(`htmlFor`), 저장 중 `aria-live="polite"` 상태 안내(기존 `structuring`
    상태 패턴 재사용 가능 — `RecordDetail.tsx`에 이미 있는 `aria-live` 관례 참고).
  - 원본 이미지에 `alt` 텍스트 필수(예: "업로드된 원본 문서 이미지").
  - 키보드만으로 편집 모드 진입→수정→저장이 가능해야 함(포커스 이동이 자연스러워야 함).
  - 명도 대비 AA(하이라이트 배경색 선택 시 텍스트 대비 재확인 — (a) confidence 하이라이트 구현 시 특히 중요).

### 3-2. 텔레그램: 인라인 버튼 + 대화형 수정

기존 `/structure` 명령의 대화 흐름(`context.user_data["last_ocr_text"]`에 마지막 결과를 담아두고
다음 명령에서 참조하는 패턴, `telegram_bot/handlers/ocr_handlers.py` 실측)을 재사용한다.

**흐름**:
1. OCR 결과 회신 메시지 하단에 인라인 키보드 버튼 `[✏️ 수정하기]` 추가(`InlineKeyboardMarkup`).
2. 버튼 클릭(`CallbackQueryHandler`) → 봇이 "수정할 텍스트를 입력해주세요" 안내 메시지 전송 +
   `context.user_data["awaiting_correction_for"] = record_id` 로 상태 저장.
3. 사용자가 다음 메시지로 새 텍스트를 보내면, 해당 핸들러가 `awaiting_correction_for`를 확인해
   `corrected_text`로 저장하고 "수정 완료" 회신.
4. 타임아웃(예: 5분 무응답) 시 `awaiting_correction_for`를 초기화해 무한 대기 방지.

이 흐름은 웹의 "저장" 액션과 동일한 백엔드 갱신 로직(§4의 `update_corrected_text` 같은 storage 함수)을
공유해야 한다(feature-consistency-guideline.md 대칭 원칙 — 텔레그램/웹이 같은 core 함수 재사용).

## 4. 데이터 모델 영향(제안 — 실제 마이그레이션은 이번 스코프 아님)

`core/storage/db.py`의 `ocr_records` 테이블(현재 스키마는 `docs/tech-spec.md` §7 참고)에 다음 컬럼
추가를 제안한다.

| 제안 컬럼 | 타입 | 설명 |
|---|---|---|
| `corrected_text` | TEXT, nullable | 사람이 수정한 최종본. `extracted_text`(OCR 원본)는 절대 덮어쓰지 않고 그대로 보존. |
| `is_corrected` | BOOLEAN(SQLite는 INTEGER 0/1), DEFAULT 0 | 수정 이력이 있는지 빠르게 필터링하기 위한 플래그. |
| `corrected_at` | TEXT, nullable | 마지막 수정 시각. |
| `original_confidence` | REAL, nullable | `classify_image`가 계산한 평균 confidence를 저장해두면, 사후에 "이 레코드가 애초에 신뢰도가 낮았는지" 조회 가능(현재는 분류 게이트에서만 쓰고 버려짐). |

**설계 원칙**: `extracted_text` 컬럼은 그대로 두고 `corrected_text`를 새로 추가하는 이유는 §1-3 성공
기준(원본 보존)을 만족시키기 위함이다. API 응답에서는 "표시용 텍스트"를 `corrected_text ?? extracted_text`
(수정본이 있으면 그것을, 없으면 원본을) 우선순위로 반환하는 헬퍼가 필요하다(`record_to_dict()` 확장 지점,
`docs/tech-spec.md` §7 참고).

**API 영향(제안)**: `PATCH /api/records/{id}` 신설(REST 관례상 부분 수정=PATCH, `docs/tech-spec.md` §9의
기존 엔드포인트 표와 일관된 스타일). 요청 바디 `{correctedText: string}`, 응답은 `record_to_dict()` 그대로
재사용해 camelCase 유지(naming-standard.md).

## 5. 구현 우선순위 로드맵

과설계 방지를 위해 단계별로 쪼갠다. 각 단계는 독립적으로 배포 가능해야 한다.

| 단계 | 내용 | 선행 조건 |
|---|---|---|
| **1단계**(권장 최우선) | DB 스키마 확장(§4) + 웹 RecordDetail 원본대조·수정 UI + `PATCH /api/records/{id}` | 없음(바로 착수 가능) |
| **2단계** | 텔레그램 인라인 버튼 + 대화형 수정 흐름(§3-2) | 1단계의 백엔드 저장 로직 재사용 |
| **3단계** | (a) confidence 기반 하이라이트 — 1단계 UI에 얹는 점진적 개선 | 1단계 완료, `classify/engine.py`의 단어별 confidence를 노출하는 API 확장 필요 |
| **4단계**(장기) | (c) 구조화 정합성 휴리스틱 — §14-1 구조화가 더 안정화된 뒤 검토 | §14-1 구조화 기능의 신뢰도 확보 후 |

각 단계는 별도 `a_*` 지시서로 분리해 진행할 것을 제안한다(이번 문서는 설계까지만, och.txt 규칙 A-2 준수).
