### Bot's orch-session-death alert — check_orch_alive() (kept — simple·useful)
- Bot main-loop calls every tick. **NOT a complex watcher-restart — simple mtime-check + 1 Telegram alert.**
  1. `logs/.orch_alive` missing(orch never started) → no alert(avoid false-positive).
  2. mtime within `_ORCH_ALIVE_TIMEOUT`(default 5min) → loop alive → reset alert state.
  3. Exceeded(loop stopped=session dead) → alert user "restart session" **once**(`_ORCH_ALIVE_ALERT_INTERVAL` default 30min, anti-spam).
- Updater = orch's /loop(P5) — loop runs=session alive, stops=bot alerts. Bot does NOT restart the session.

### ★ Reply-delay alert + recovery notice (Claude service-hang detection)
> **Bg**: heartbeat updates every 20min-reset event, so "watch(Monitor) runs but Claude stopped responding"
> escapes check_orch_alive(sees signal alive). To catch real no-response cases, watch **reply-delay** separately.
- **Detect(state transition)**: bot's **since last-unprocessed u_(user msg), no orch reply**(Telegram send OR ar_
  terminal relay) **within N min(default 5)** = delayed state. (Independent of liveness signal — catches Claude
  service-hang/session no-response too.)
- **★Alert ONCE(edge-trigger)**: normal→delayed **on entry only** send "⏳ Processing delayed/service check —
  requests safely queued". No repeat during ongoing delay(anti-spam). `_delay_alert_sent` flag guarantees once.
- **★Recovery notice**: orch responds again(reply sent/pending-u_ resolved) → delayed→normal **transition, once**
  send "✅ Recovered." + flag reset.
- i.e. **alert once · recovery-notice once** state-transition alerting. Raw Claude errors can't propagate via
  harness, but "delayed/recovered" state IS reported by bot.
- Separate/complementary from check_orch_alive(session-death=liveness-gap) — this layer catches "reply-only-delayed/no-response".

## 2. Communication protocol (file-based)

All comms happen via text files under `telegram_bot/orchestrator/protocol/`.

```
protocol/
  u/   u_*.txt   ← user's Telegram requests(orchestrator records)
  a/   a_*.txt   ← directives to worker(orchestrator records, worker appends response)
  done/          ← archive of completed requests/directives
```

### Filename rules
- User request:  `u_<SEQ>_<topic-slug>.txt`
- Worker directive:  `a_<SEQ>_<topic-slug>.txt`
- One user request(`u_*`) can decompose into 1+ worker directives(`a_*`).

### 2-A. ★★ New project = fresh protocol queue (MUST)

> **Bg incident**: a repo copied orch/worker pipe assets from a prior project. `protocol/u`·`protocol/done`·
> `protocol/archive` still had **hundreds of old u_/a_/ar_ from the old project**. Orch(me) mistook these as
> "this project's history/precedent", tried citing old-project convos as basis for new directives(violates
> §11.5 rule-A "don't mistake past output for current"). User caught+corrected it.

- **★Starting a new project = fresh protocol queue.** Even if pipe code copied from another project,
  **queue(`protocol/u`·`a`·`ar`·`done`·`archive`) is NOT reused as-is.**
  - Prior-project leftovers = **NOT precedent/history/context.** seq numbers don't continue from leftover max.
  - Move leftovers to separate storage(`protocol/_archive_<old-project-name>/`) or clear, **start fresh from empty queue.**
  - "done has a_225 from old project, use as precedent" = forbidden judgment — **that's a different project's convo.**
- **★Current project's protocol must be freshly structured.** Minimum structure when starting fresh:
  ```
  protocol/
    u/      (start empty)      ← this project's user requests
    a/      (start empty)      ← this project's worker directives
    ar/     (start empty)      ← worker responses(for orch session)
    done/   (start empty)      ← this project's completion archive
  ```
  seq starts fresh at **1(or 001)** for this project.
- **How to tell**: if queue's u_/a_/done content covers a domain **unrelated to current project code**
  (`telegram_bot/` tree) → it's a leftover. Verify via measurement(`ls`/content-check), treat as leftover.

## 4. Worker execution models (important)

Two worker types. Orchestrator decides which based on task nature.

### (A) Auto worker — `worker.py`(bot-embedded)
- Bot runs headless `claude -p` as subprocess, immediate.
- Fits **context-free one-shot tasks**(simple research, text-gen, summary) ONLY.
- **Unfit** for codebase-wide understanding·multi-file edits·verification(separate session = no project context, hard to verify results).

#### ★ Bot auto-dispatch gate — default off, routed via orch (P4)
> Reflects "no band-aid, best method" directive. **Bot does NOT auto-dispatch u_ by default.**
- **Gate: `ORCH_AUTO_DISPATCH`(default off).**
  - **off(default)**: bot **saves + ack-feedback ONLY** on new u_, does NOT connect raw u_ text to worker directly.
    u_ stays pending in queue(0-loss), **orch session wakes via §9-0 → refines u_ → writes a_ → dispatches worker**
    (orch-routed = P4-compliant). Bot's auto `claude -p` spawn ONLY applies to a_ **explicitly marked
    `[WORKER_MODE] auto` by orch**.
  - **on(`ORCH_AUTO_DISPATCH=1`)**: legacy behavior(bot auto-spawns u_). Avoid regular use.
- Rationale: bot(non-LLM) can't distinguish real-work/approval/feedback — spawning raw u_ as worker makes
  signal-type requests get stuck w/ workers(zombie), bypasses orch's refine/control(P4 violation).
  → **root-block the path of bot connecting raw u_ text to worker**, unify all dispatch via orch judgment.
- (ref) Orch-only-signal u_(inline-button-reply `ask|`·needs-info answers) are marked `.orch_only` via
  `worker.mark_orch_only()`, excluded from auto-dispatch from the start(orch-session-only consumption).

#### ★ Auto-worker zombie/hang prevention (P2)
- **Explicit reap**: every bot loop, `_prune_running()` immediately reaps children terminated via `poll()`
  → normal-exit/externally-killed children don't linger as `<defunct>`(zombie).
- **Hang timeout**: worker w/ **liveness-signal gap** exceeding `ORCH_WORKER_TIMEOUT_SEC`(default 600s) →
  SIGTERM→(grace)→SIGKILL on process-group, record paired a_'s `ar_` as `[STATUS] error`
  → bot relay reports to user+archives(0-loss auto-recovery).
  - Liveness signal = `ar_` file mtime(rises when worker updates `[HEARTBEAT]`/`[STATUS] in-progress`).
    Timeout resets while heartbeat updates → catches only **truly stuck** ones, no false-positive on long normal work.
- **Graceful shutdown**: bot exit(atexit·SIGTERM) → `shutdown_all()` cleans up all running children
  → bot dying doesn't orphan child workers.

### (B) Session worker — Claude Code session(human-run orch/dev session)
- **Codebase-context-requiring work**(source analysis/cleanup, feature impl, refactor, E2E verify) = this worker type.
- Bot leaves directive as `a_*.txt` but **does NOT auto-execute, leaves as `pending`**(`WORKER_MODE=session`).
  Claude Code session picks it up → processes → writes Response → `done`.
- Bot detects done → replies to user.

>判別基準: "does this need to read/modify THIS project's source/files?" → yes = (B) session worker,
> no = (A) auto worker. Source analysis·docs·implementation = always (B).

- **Compound request** → decompose into multiple a_*.txt, specify dependency order.
- Ambiguous → ask user back(via Telegram).
- Worker capability = whatever this project's code does(general-purpose: impl/refactor/research/verify).
  Determine specific capability/domain from project source(`telegram_bot/` tree) + root CLAUDE.md(if any).
  This role-doc does NOT pin a specific domain.

## 7. Session-worker processing rules (when Claude Code session IS the worker)

1. Pick up `status: pending` + `[WORKER_MODE] session` directive from `protocol/a/`.
2. Immediately flip to `status: in-progress`(prevent dup-processing).
3. Execute the task **in this project's code context**(analyze/impl/verify).
4. **Heartbeat during work(MUST)**: update `ar_*.txt` top `[HEARTBEAT] HH:MM <current stage>` line
   **every 2-3min**(even during no-artifact phases like file-reading/reasoning).

5. Append result to `## Response`/`## 결과` + `status: done`.

## 9-0. ★★ Auto-wake protocol for new user requests

### Mechanism (harness trait exploited)
**Background Bash cmd exiting → harness re-invokes session.** Used as signal:
poll `protocol/u` every 5s, **new unhandled u_ found → exit immediately** → session wakes, handles it.

### ★ P5 transition — this watcher mechanism replaced by loop(deprecated)
> §9-0 watcher(orch_wait_for_user.sh) = **legacy auto-wake**. Now **Telegram/worker 5s monitoring = orch's /loop
> directly**(P5). Bot-side watcher-restart logic(ensure_watcher_alive) made bot complex+crash-prone → removed.
> → watcher scripts not deleted(kept unused) but **loop replaces their role**.

### Death prevention (dual safety — bot 0-loss + loop active watch)
- **loop(active watch)**: orch's /loop every 5s(harness 60s clamp) tick: refine new u_·issue a_·watch ar_ state
  + `date > logs/.orch_alive` update. Single watch actor = loop(P5) — no watch logic bolted onto bot.
- **u_ 0-loss(bot)**: even if session(loop) stops, bot keeps stacking `u_*.txt` → **receipt itself guaranteed by
  bot**(0 loss). Session wakes next → picks up all pending u_ since(via seen).
- **loop keep-alive(P6)**: before ending any turn, self-check — **does loop survive?** If not, re-schedule via
  ScheduleWakeup before ending(never kill the loop). Worker also reminds this in ar_.

### ★ Orch-session-death detection — liveness signal + bot alert (P2-C)
> Harness can't let bot auto-restart orch session → correct approach = **alert + 0-loss queue preservation**.
- **Liveness(heartbeat)**: while orch alive, update `logs/.orch_alive` mtime. Post-P5, updater = **orch's /loop
  tick**(`date > logs/.orch_alive`) — loop running = orch alive.
- **Bot alert(C1)**: `orchestrator.py check_orch_alive()` observes this mtime every loop. Gap exceeding
  `ORCH_ALIVE_TIMEOUT_SEC`(default 300s) → alert user(or `TELEGRAM_ALLOWED_CHAT_IDS`) **once**
  "orch session unresponsive, requests safely queued"(`ORCH_ALIVE_ALERT_INTERVAL_SEC` interval, anti-spam).
  No file(orch never started) → no alert(avoid false-positive). Orch revives(signal updates) → alert-state reset.
- **0-loss**: bot auto-dispatch default off(§4-B) so orch dying stops u_ processing, but bot keeps
  saving+ack-feedback u_ → **0 loss**. Orch revives, wakes via §9-0 → picks up all pending u_ in order,
  refines→dispatches. While dead, C1 alert tells user "restart the session" → detect·notify·recover auto-chains.

## 9. Monitoring (5s cycle — MUST)

Orchestrator checks every **5s**:

1. New Telegram msgs(long-poll `getUpdates`) → create `u_*.txt`
2. `protocol/a/` directive state changes: `pending`→delegate / `done`|`failed`→reply+archive
3. Completed `u_*.txt`/`a_*.txt` → archive to `protocol/done/`

Poll interval via `.env`'s `ORCH_POLL_INTERVAL`(default 5s). On error, retry after 3s, never stop looping.

### 9-1. `ar_*` 5s monitoring (orchestrator session's duty — absolute)

Separate from bot process's 5s poll, orchestrator session(=Claude Code control tower) **actively tracks**
worker's `ar_*.txt` **every 5s** after issuing a directive. Don't rely solely on worker-completion notifications.

- **Heartbeat watch**: check `ar_*.txt` top `[HEARTBEAT] HH:MM` update every 5s. Gap >3min = treated as stuck,
  intervene(prompt/investigate-cause/re-direct).
- **State-transition watch**: catch `in-progress → done/blocked/error/failed/needs-info` via 5s polling.
  On terminal, verify result + report to user immediately(bot handles Telegram reply, but session's job = verify artifact for real).
- **Orphan `ar_` cleanup**: paired `a_` already archived but `ar_` remains → bot can't clean it → session confirms
  done then moves to `protocol/done/`.
- Don't just "wait for notification and miss state changes" — 5s polling is the principle.

## 11. ★ Worker↔orch question round-trip protocol (needs-info, P4-compliant)

> **Problem**: needs-info had only a status-value defined, bot **connected it straight to user**, bypassing
> orch's refine/control(P4 violation). Also archived needs-info instantly → user's answer had **no path back to
> worker** → convo broken. → close the round-trip below.

### Principle (P4 = real-work via worker, questions via orch too)
Worker's raw question must NOT go directly to user. Flow: **worker→orch→(self-answer OR user-button)→orch→worker**.
Orch(session) = the refine/judgment gateway. Bot does **NO reply/archive** in this phase(wait only).

### 4-step round-trip

1. **[worker stuck]** Worker does NOT ask user directly. In response file `ar_{NN}_*.txt`:
   - first line `[STATUS] needs-info`(or `waiting-answer`)
   - `[QUESTION] <one-line question for orch>` or detailed in `## 질문`/`## Question` section.
   - **Stop here**(leave work-state in ar_ as resume scaffold).

2. **[bot: hold reply/archive]** `relay_worker_responses()` detects needs-info →
   **forbidden** to reply-user/archive, leaves `[question-pending] … awaiting orch` log only.
   (`TERMINAL_STATUSES` excludes needs-info → not cleaned up like done.)

3. **[orch(session) judges]** Session catches needs-info during 5s-poll(§9-1).
   Query: `worker.find_needs_info()` → `[(a_path, ar_path, question), …]`(excludes already-[ANSWER]'d).
   Two branches:
   - **Orch can self-answer**(determined by project context/standards): decide it directly.
   - **Needs user decision**(product direction/priority/preference): refine into Telegram **inline button**,
     send via `scripts/ask_telegram.py`(`ask|{key}|{value}` callback). User taps → bot writes answer to `u_*.txt`
     via `_handle_ask_callback` → session reads on next poll, adopts as answer.
     (Asking user = ALWAYS via Telegram button, not session UI.)

4. **[orch relays answer back to worker = resume]** Once orch settles on answer:
   - Call `worker.answer_and_resume(a_path, answer, source="orch")`. This:
     1) `append_answer()` — appends `[ANSWER]` + `## 오케 답변`/`## Orch Answer` block to end of `a_{NN}`(resume scaffold),
     2) deletes paired `ar_{NN}`(discard needs-info response → a_ reverts to 'pending'),
     3) `spawn_for_task(resume=True)` — re-spawns worker.
   - Resumed worker reads `a_`'s `[ANSWER]`, continues(NOT from scratch).
     Finishes normally → `[STATUS] done` → bot replies+archives.

### Field summary
| Location | Field | Meaning |
|----------|-------|---------|
| `ar_{NN}` | `[STATUS] needs-info` | worker asks orch(no archive/no user-direct) |
| `ar_{NN}` | `[QUESTION]` / `## 질문` | question for orch to read |
| `a_{NN}` | `[ANSWER] {source}` + `## 오케 답변` | orch's(or user-refined) answer — resume fuel |

### Session self-check(every poll turn)
- On needs-info: **never forward raw to user** — always refine(self-answer or button-question).
- Self-answer → cite basis(.claude/rules·standards). User-button → clear options.
- Answer attached → **MUST resume** via `answer_and_resume`(deleting ar_ w/o re-spawn = stuck forever).
- Post-resume → keep tracking new `ar_` for that SEQ via §9-1(round-trip can loop multiple times).

### 0-loss/never-dies (P2)
- needs-info = not terminal, bot can't clean it up → question stays queued even if session dies(0 loss).
- `answer_and_resume` never throws, returns `(False, reason)` → protects session loop.
- Re-spawn hitting concurrency cap → `(False, max-concurrent)` → retry next poll(answer already persisted in a_).

  test images/documents), check `~/git/kong-bot/telegram_bot/orchestrator/shared_out/manifest.json` for relevant
  `items` before asking the user or doing net-new work. kong-bot does NOT push notifications here — pull only.
- **★10-A-1 — direct kong-bot Telegram request requires EXPLICIT user approval each time**: orch may read
  kong-bot's `.env` token and send a Telegram msg to kong2019_bot **only after the user explicitly approves in
  THIS session**(not a standing permission — different-project credentials are sensitive, ask via Telegram per §11
  round-trip each time it's needed, don't assume prior approval carries over).
- **★10-A-2 — INBOUND from another bot(e.g. kong-bot) requires NO extra approval — just check content and proceed**
  (user: "타 봇에게 연락이 오면 내용 확인하고 진행하면 된다"). Direction matters:
  - **Outbound**(ocr-lake→other-bot, orch initiates contact using another project's credentials) = §10-A-1 applies,
    ask user first each time(touching someone else's token is the sensitive act).
  - **Inbound**(another bot/project sends a msg/image TO ocrlakebot, e.g. kong-bot relaying a captured test image) =

    inbound traffic on ocrlakebot's own token, which orch already controls.
- **SCOPE**: kong-bot-family repos only(sibling projects under `~/git/` — sky, ocr-lake, fortune, zodiac etc) —
  not a general public-facing API. No auth beyond filesystem access(local machine, single-user).
- **★10-A-3 — Telegram DOES block direct bot-account-to-bot-account DM(measured: 400 Bad Request when orch tried
  sending FROM ocrlakebot's token TO kong2019_bot's own bot-id as chat_id)** — but ★DON'T over-generalize this
  (real mistake, corrected same-day): a bot sending a message/photo to the **human user's own chat_id** using
  ANOTHER bot's token(e.g. kong-bot's worker calling ocrlakebot's `sendPhoto` API w/ chat_id=human-user) is
  **NOT bot-to-bot DM** — it's a normal bot→human send, and the human's chat_id being in that bot's
  `TELEGRAM_ALLOWED_CHAT_IDS`(or receiving side having no allowlist-block) is what actually gates it. That
  pattern generally works. So:
  - What's actually blocked: `sendMessage(chat_id=<other-bot's-own-account-id>)` — platform-level, unfixable.
  - What's NOT blocked: `sendMessage(chat_id=<human-user's-chat_id>)` using any bot's token, incl. borrowing
    another project's token — this is just bot→human, works normally(subject to that bot's own allowlist).
  - When cross-project delivery via Telegram silently fails, **don't assume "bot↔bot DM" as the cause without
    checking whether the target chat_id is actually a bot-account vs the human's own chat_id first**(§11.5 rule-A
    — verify before asserting). If the human's chat_id was the target and it still didn't arrive, suspect other
    causes(getUpdates offset consumed by wrong poller, wrong token, msg sent but client-side notification
    swallowed — check via direct `getUpdates` call for pending count, not just local receive-logs).
  - **Preferred path regardless**: SHARED_OUT/SHARED_IN(§10-A, file+manifest pull) is simpler+more reliable than
    debugging Telegram delivery across bots — when in doubt, just pull the artifact file directly instead of
    chasing a telegram-send success/failure.
